# TrustVisor — ядро проверки подлинности

Здесь открыт код, которым проверяется подлинность файлов, снятых приложением
TrustVisor: разбор пакета, сверка подписи, проверка цепочки аппаратной
аттестации и вычисление вердикта.

**Зачем это открыто.** Мы говорим клиентам, что проверку можно повторить без
нас. Утверждение стоит ровно столько, сколько стоит возможность его проверить.
По этому коду и спецификации можно написать собственный проверяльщик и убедиться,
что наш вердикт не подкручен.

---

## Что доказывает подпись, а что нет

Честно и сразу, чтобы не создавать ложных ожиданий.

**Доказывает:** что файл снят конкретным устройством, что ключ подписи рождён
внутри защищённого чипа этого устройства и никогда его не покидал, и что с
момента съёмки не изменился ни один байт — ни в изображении, ни в метаданных.

**Не доказывает:** что перед объективом была настоящая сцена. Камера,
направленная на монитор, снимает настоящие лучи, и подпись сойдётся честно.
Это ограничение любой подобной системы, и **автоматического** решения у него
нет: программа, объявляющая «похоже на съёмку экрана», ошибалась бы в обе
стороны, и цена ошибки — чужая правота в споре.

Что тут можно сделать, мы делаем. К видео прикладывается журнал показаний
собственных датчиков телефона за время съёмки — ускорение, повороты, магнитное
поле, освещённость, — и его отпечаток лежит внутри подписанного манифеста, так
что подогнать журнал под картинку нельзя. Съёмка с экрана расходится с журналом
почти всегда: телефон поворачивается, а картинка стоит; в кадре улица, а света
ровно столько, сколько в комнате. Вывод из этих расхождений делает человек,
разбирающий спор, а не проверяющий код.

## Две версии формата

В обращении два формата, и проверяющий понимает оба.

**1.x** — подпись лежит полем `signature` внутри манифеста, а подписанные
байты восстанавливаются по списку полей. Файлы 1.x остаются проверяемыми
всегда: правила для них заморожены.

**2.0** — подпись вынесена в отдельную запись `<имя манифеста>.jws`
(RFC 7515, компактная отсоединённая форма, `b64:false` по RFC 7797) и
покрывает **сырые байты манифеста**. Восстанавливать ничего не надо — а
именно восстановление и было источником закрытых дыр. Цепочка аттестации
переехала в защищённый заголовок `x5c` и тем самым впервые оказалась под
подписью. Различаются форматы по наличию записи `.jws`; отката нет ни в одну
сторону.

К пакету 2.0 может добавляться необязательная запись `sensors.bin` — журнал
показаний датчиков за время съёмки. Проверяющий сверяет её хэш и показывает
содержимое, но **никаких выводов из него не делает**: правдоподобие движения
— вопрос к эксперту, а не к программе.

Подробно — разделы 2.0 и 1.7 спецификации.

## Главное свойство: два проверяльщика обязаны отвечать одинаково

Проверка работает в двух местах — в браузере у получателя файла и на сервере.
Они написаны на разных библиотеках разбора архивов, и **любое расхождение между
ними — ошибка**, даже если оба ответа выглядят разумными.

Причина не теоретическая. Расхождение бьёт не только по «подделка прошла», но и
по обратному: если один проверяльщик отказывается открыть честный файл, которому
другой говорит «подлинно», получатель решит, что доказательство поддельное.
Дискредитировать настоящее доказательство дешевле, чем подделать.

Поэтому в `tools/` лежит то, чего обычно не публикуют: **перебор**. Берётся
настоящая съёмка, портится всеми способами, какие мы придумали, и оба
проверяльщика прогоняются по всему набору с посимвольным сравнением вердиктов.
Ожидаемый результат — ноль расхождений. Число случаев зависит от переданного
файла: на образце из `samples/` их получается 301.

Оговорка, без которой набор читается неверно: сравниваются **вердикты двух
реализаций**, а не «все обязаны провалиться». Часть случаев и должна дать
ПОДЛИННО — см. раздел «Перебор».

Этот перебор находил то, что не находило чтение кода. В том числе обход правки,
сделанной за час до него.

## Запуск

Нужен **Node 22.6 или новее**: проверки идут через `--experimental-strip-types`,
на более старых он недоступен. Питон нужен только для сборки производных
образцов и наборов перебора.

Что проверяется на каждый push — в `.github/workflows/ci.yml`: сборка, все
проверки, затем подлинный образец обязан пройти, а испорченный и
неаттестованный — не пройти. Последним шагом собирается и прогоняется набор
перебора — три сотни порч одной настоящей съёмки.

### Проверить файл

```bash
npm install
npm run build
node tools/verify.mjs samples/genuine-photo.trustvisor
```

Печатает вердикт, момент съёмки, устройство и состояние каждой проверки с
пояснением. Принимает и подписанное медиа — `.jpg`, `.png`, `.mp4`, — то есть
те же файлы, что отдаёт приложение кнопкой «поделиться как медиа».

Код возврата: `0` — ПОДЛИННО, `1` — вердикт хуже, `2` — файл не наш. Так
проверку можно звать из скрипта, а не только читать глазами.

Отказ разобрать — это **не** вердикт «изменён». «Изменён» означает, что
доказательство испорчено; «не наш формат» — что прислали не тот файл. Разница
существенна для получателя, и проверка её не смешивает.

### Прогнать проверки

```bash
npm test
```

Проверки не ходят в сеть и ничего не требуют настраивать: настоящие
подписанные файлы лежат в `samples/` и берутся оттуда сами. Свои можно
подставить переменными `TV_REAL_PACKAGE` (фото) и `TV_REAL_VIDEO` (видео).

Ещё две проверки включаются, если сделать производные образцы:

```bash
python samples/make_samples.py
npm test
```

Положительные проверки не менее важны отрицательных: заслон, который отвергает
честный файл, — такая же поломка, как пропущенная подделка.

### Перебор

```bash
python tools/fuzz_gen.py samples/genuine-photo.trustvisor  # собрать набор порч
node   tools/fuzz_server.mjs tools/corpus > verdicts.json  # прогнать через ядро
node   tools/fuzz_check.mjs verdicts.json                  # сверить с правилом
```

Набор строится из того файла, который передан: имена случаев и их состав
зависят от полей его манифеста. На образце из `samples/` получается 301
файл.

**Что считать успехом.** Не «все обязаны провалиться»: одиннадцать случаев
дают ПОДЛИННО, и это правильно. Первый из них — `000_clean`, неиспорченный
контрольный файл; если бы он не прошёл, сломан был бы сам проверяющий.
Остальные десять меняют то, что подписью не покрыто: переводы строк,
табуляции и пробелы в манифесте, порядок записей в архиве, способ сжатия,
форму дескриптора. В формате 1.x подпись считается по восстановленной форме,
и такое форматирование её не меняет — это прямо сказано в §3.3
спецификации. (В формате 2.0 подписаны сырые байты, и те же случаи дадут
ИЗМЕНЁН.)

Это правило сверяет `tools/fuzz_check.mjs`, а не читатель глазами: в трёх
сотнях строк одна изменившаяся не замечается, а именно она и означала бы, что
порча начала проходить. Восемь названных пересборок ВПРАВЕ дать ПОДЛИННО,
любой другой случай с таким вердиктом — поломка; контрольный файл и две
раскладки дескриптора, наоборот, пройти обязаны. Тот же прогон стоит в
сборке.

Настоящая проверка здесь другая: прогнать набор через обе реализации и
сравнить вердикты посимвольно. Расхождение — ошибка, даже если оба ответа
выглядят разумными.

Третий набор портит **подписанное медиа** — второй контейнер формата, где
подпись лежит не в архиве, а в боксе MP4, чанке PNG или хвосте JPEG:

```bash
python tools/fuzz_media.py настоящее_подписанное.jpg      # tools/corpus-media
node   tools/fuzz_server.mjs tools/corpus-media
```

Длины блоков, версии, перестановка манифестов начала и конца, набивка после
манифеста, магия дважды. Долго этот контейнер стерегли три теста — а читают и
пишут его обе реализации, и мест, где раскладка задана байтами, около двух
десятков.

Второй набор — не случайные порчи, а двадцать два случая, каждый из которых
когда-то приводил к тому, что браузер и сервер отвечали по-разному:

```bash
python tools/make_corpus.py                                # tools/corpus-divergence
node   tools/fuzz_server.mjs tools/corpus-divergence
```

Вердикты этого набора имеет смысл сравнивать с ответами браузерной проверки на
[trustvisor.ru/proverit-fayl.html](https://trustvisor.ru/proverit-fayl.html):
расхождение — это баг, даже если каждый ответ по отдельности выглядит разумным.

## Проверка не обращается к сети

Это принципиально, а не оптимизация. Проверка обязана работать, когда нас нет:
без интернета, без обращения к нашим серверам, без доверия к нам. Всё, что нужно
для вердикта, лежит внутри самого файла и в списке доверенных корней.

**Отзыв ключей аттестации при этом проверяется.** Google ведёт список ключей,
которые скомпрометированы: обладатель такого ключа собирает цепочку, проходящую
проверку корня, и объявляет в ней что угодно — заблокированный загрузчик,
StrongBox, свой публичный ключ, — не притрагиваясь к телефону. Без этой
проверки утверждения об устройстве теряют смысл: все они читаются из той же
цепочки.

Размен решён не выбором, а разделением. Здесь лежит **снимок списка с датой**
(`revoked-keys.ts`), и дата уходит в текст проверки: «список отзыва на такое-то
число». Обещание работать без сети сохраняется, а читатель знает, на какое
число дан ответ. Кто проверяет онлайн, передаёт свежий список доводом
`verifyPackage(entries, { revoked, revokedDate })` — тогда снимок не
используется. Обновить снимок: `python tools/update_revoked.py`.

Честная оговорка: ключ, отозванный после даты снимка, проверкой без сети не
будет замечен. Свежий список берите сами — это предпочтительнее нашего снимка.

## Чего здесь нет

Не открыты сервер лицензий, личный кабинет и само приложение: там вход, платежи
и админка — открывать их значит выдать карту атакующему.

Открыто ровно то, что нужно, чтобы повторить проверку и убедиться в её честности.

## In English

**What this is.** The verification core of TrustVisor: it decides whether a
photo or video was really taken by the device that claims it, and whether a
single byte has changed since. Package parsing, signature checking, hardware
attestation chain, verdict.

**Why it is open.** We tell customers the check can be repeated without us.
That claim is worth exactly as much as the ability to test it. With this code
and the specification you can write your own verifier and confirm our verdict
is not rigged.

**What a signature proves:** that the file was captured by a specific device,
that the signing key was born inside that device's secure chip and never left
it, and that no byte has changed since — neither in the image nor in the
metadata.

**What it does not prove:** that a real scene was in front of the lens. A
camera pointed at a monitor records real light, and the signature verifies
honestly. This is a limit of any such system and it has no solution.

**Verdicts.** `ПОДЛИННО` — genuine, everything checks out.
`МОМЕНТ НЕ ПОДТВЕРЖДЁН` — the file and the device check out, but the moment of
capture cannot be confirmed. `НЕ АТТЕСТОВАНО` — signatures and hash are valid,
but hardware origin is not confirmed. `ИЗМЕНЁН` — tampered. A file that is not
our format is refused rather than judged.

**The central property.** The check runs in two places — in the recipient's
browser and on our server — written against different archive libraries. Any
disagreement between them is a bug, even when both answers look reasonable.
Discrediting real evidence is cheaper than forging it, so a verifier that
rejects an honest file breaks the product just as thoroughly as one that
accepts a forgery. `tools/` therefore contains the thing usually kept private:
a fuzz corpus of mutations of a real capture — 301 of them for the sample
shipped here — run through both verifiers with per-case comparison. The
expected result is zero disagreements.

**No network.** Verification must work when we are gone: offline, without
calling our servers, without trusting us. Everything needed for a verdict is
inside the file and in the pinned root list.

**Attestation key revocation is checked.** Google publishes a list of
compromised attestation keys; whoever holds one can assemble a chain that
passes root verification and claim anything in it — locked bootloader,
StrongBox, their own public key — without touching a phone. The trade with
offline verification is resolved by splitting it: a dated snapshot ships here
(`revoked-keys.ts`) and its date appears in the check text, so the reader knows
as of when the answer holds. A verifier that is online passes a fresh list via
`verifyPackage(entries, { revoked, revokedDate })`. A key revoked after the
snapshot date will not be caught offline — fetch the list yourself if you can.

**Where to start.** `docs/SPEC_TRUSTVISOR_FORMAT.md` — the format and the exact
order of checks, including the rules that produce each verdict. `SECURITY.md` —
how to report a finding, and the defects we have already found and fixed. Code
comments and documentation are in Russian; the specification is the place to
begin if you do not read it.
